# Full Repository Pipeline & Code Review (2026-03-04)

## Scope and Method
- Scope: maintained repository files (source, scripts, UI/API, docs, configs) excluding generated/vendor/runtime artifacts (`ui/node_modules`, `ui/dist`, `build`, `runs`, `reports`, `output`, `logs`, binaries).
- Reviewed files: **167** text/code/config files, with smoke validation via `make -j$(nproc) test_smoke` (**38 passed, 0 failed**).
- Review focus: pipeline clarity, correctness, performance constraints, maintainability, and experiment reproducibility.

## Pipeline Overview
1. **Build pipeline**: `Makefile` compiles core + model families + benchmark executables, with OpenMP and optional CUDA auto-detection (`USE_CUDA=auto|0|1`).
2. **Execution pipeline**: each benchmark binary trains/evaluates a model family and emits run artifacts through `RunLogger` into `runs/<run_id>/...`.
3. **Bio addon pipeline**: benchmarks optionally attach `BenchBioHarness`, which drives `BioRuntime` hooks (`before_forward`, `after_backward`, `after_optimizer_step`, epoch snapshots).
4. **Control benchmark pipeline**: `DiscreteEnv` + `BitBridgeModel` + `DiscreteQRuntime` decouple benchmarks from model internals (TicTacToe/games/chess/cartpole/etc.).
5. **Continuous-learning pipeline**: `ContinuousRuntime` alternates active/sleep phases with replay and noise to simulate always-on training cycles.
6. **Optimization pipeline**: `scripts/random_search.py` runs architecture-specific random HPO; `scripts/bio_sweep_queue.py` runs combinatoric bio ablations.
7. **Analytics pipeline**: Python plotting (`analytics/plots`) produces report images from run CSVs; Streamlit dashboard provides quick exploratory views.
8. **Live UI pipeline**: React app + Express API (`ui/src/App.jsx`, `ui/api/server.mjs`) provide live run/task orchestration, benchmarking filters, model-specific visuals, and game replay.

## Cross-Cutting Critical Review
### Strengths
- Strong benchmark/model decoupling through `TrainableModel` and bit-bridge/discrete-env interfaces.
- Run artifact schema is broad and consistent enough to power both analytics scripts and live dashboards.
- Core numerics and guardrails have improved (loss/metrics checks, robust run-id generation, heartbeat-based activity).
- Bio runtime is now an actual configurable mechanism layer (not just placeholders), with structured telemetry for ablations.

### Main Technical Debt
- **Frontend/API complexity concentration**: `ui/src/App.jsx` and `ui/api/server.mjs` are monoliths; this is the highest regression risk area.
- **Synchronous API IO under polling load**: backend reads/parses CSVs synchronously and repeatedly; this can stall under many active runs.
- **Benchmark code duplication**: supervised benchmarks repeat substantial train/eval/log loops; control benchmarks (`benchmark_tictactoe.cpp` and `benchmark_games.cpp`) duplicate large blocks.
- **Partial adapter coverage**: hybrid/bit-bridge adapters intentionally exclude several families; this boundary must stay explicit in UI/UX to avoid user confusion.
- **GPU acceleration scope**: CUDA path currently accelerates matmul only and still performs host-device copies per call; full training is not end-to-end GPU-native.

### Recommended Next Refactors
1. Split UI monolith into feature modules and introduce a shared data store for polling/state derivations.
2. Move API filesystem access to async + mtime-indexed incremental caches, with optional SSE/WebSocket for live updates.
3. Extract common C++ benchmark harnesses (supervised loop, control loop logging adapters) to reduce duplication and drift.
4. Expand adapter registry (or hard capability manifests) so unsupported model-benchmark combinations fail early with explicit rationale.
5. Evolve tensor backend toward broader GPU kernels and reduced transfer overhead (batched ops, persistent buffers, optional mixed precision).

## Closing Assessment
- The repository is now a substantial multi-paradigm benchmark system with a coherent run schema and useful experimentation surface (bio features, continuous runtime, control games, hybrid composition, HPO orchestration, and dual dashboards).
- The codebase is functional and test-backed in core numerics, but engineering maturity is uneven: infrastructure abstractions are strong, while frontend/API and benchmark orchestration layers need decomposition for long-term reliability.
- The highest-value immediate work is architectural hardening (UI/API split, async caching, benchmark harness reuse) rather than adding more model families.
